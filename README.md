## 解决什么问题

一家公司的同一件事，会在几个月里被公告、快讯、评论、研报反复说，数字还会被公司自己改。看到其中一条消息的人很难知道：这事最早是谁说的，后来改过什么，现在算数的是哪一版。

以仓库里的第一条事件为例：\*ST国中 2025 年的扣非净利润前后有五个版本。

| 披露日 | 来源 | 扣非净利润 |
|---|---|---|
| 1-30 | 业绩预亏公告 | 盈利 900 万至 1,080 万元 |
| 4-18 | 预告更正公告 | 亏损 2,900 万至 3,600 万元 |
| 4-29 | 预告再次更正公告 | 亏损 5,976 万元 |
| 4-30 | 年报 | 亏损 5,976.21 万元 |
| 8-20 | 年报非经常性损益更正公告 | 亏损 21,462.88 万元 |

1 月那条"扣非盈利"的快讯现在还搜得到，上面没有任何"已被更正"的标记。只看其中任何一条，都会得到不完整甚至过时的结论。

样例里撞到的五类问题：

1. 消息会过期，但没人告诉你（上表）。
2. 二手转述和一手对不上，公司自己的公告之间也会对不上：国中 4-18 的更正公告把前次披露日的年份写错了；4-29 的更正公告里一个持股比例写错，5-06 又发公告更正。
3. 观点建立在会失效的前提上：科达制造 1 月、4 月有研报以"重组推进"为题，8 月重组审核未通过。
4. 状态被说粗了：科达 8-05 是"审核未通过"，8-11 是"交易所终止审核"，8-15 才是"交易终止"。媒体 8-05 的标题已经写"否决"。
5. AI 摘要没法核对：一段总结里哪句来自公告、哪句是模型补的，看不出来。

## 给谁用

- 关注个股的个人投资者：看到一条消息，想知道它是不是最新的、有没有被改过。
- 替客户盯事件的投顾助理：要给客户讲清楚一件事的来龙去脉，每句话都要有出处。

不做的：不预测涨跌，不给买卖建议，不做全市场实时监控，不做登录和推送。

## 核心设计

1. **事件合并**：先按"股票代码 + 事件类型 + 报告期或交易标的"用规则分桶，再由大模型判断是否同一件事，并写出合并理由。合并理由显示在页面上，可以被人检查。
2. **证据分类和权重**：每条证据标成事实、观点、推测、传闻四类之一。来源分五级（A 公司公告和交易所文件，B 媒体对公告的转述，C 媒体评论和研报观点，D 推测性报道和算法归因，E 传闻），权重由规则给定，不让模型打分。低级别来源不能推翻高级别来源。
3. **四种时间分开记**：发生时间（说法所指的日期或报告期）、披露时间（公告披露日或媒体发布时间，注明精度）、抓取时间、更新时间（数据源目前不提供，页面如实写"来源未提供"）。
4. **版本而不是覆盖**：被更正的数字不删除，保留为"前值"并注明被哪条证据在哪天取代。页面可以选"截至某天"，回放当时的结论。
5. **冲突单列**：证据之间对不上的地方单独列出，写明怎么处理、是公司更正的还是系统推断的。
6. **结论分三段**：事实、推断、还不确定。每句话挂证据编号，点一下跳到证据和原文片段。
7. **引用逐字校验**：模型给出的每条引用，必须能在公告正文或新闻摘要里逐字匹配到；匹配不到就拒绝生成数据文件。结论也不能引用"截至日"之后才出现的证据。
8. **数值校验**：每个版本的数必须能在它自己的引用里找到，原文单位（元、亿元）换算成展示单位后要对得上。这条是评测发现"逐字匹配只能证明原文里有这句话，证明不了数字读对了"之后加的。
9. **观点过期**：以某件事会发生为前提的观点，前提被后来的公告推翻时，标记为过期并指向推翻它的证据。
10. **自己算更新时间**：数据源不提供"事后修改时间"，所以给每条证据存正文指纹，重抓后比对（`pipeline/recheck.py`）。
11. **离线问答加 trace**：预置问题的回答每句标事实、推断、不确定或不回答，并挂证据；trace 记录取了哪些证据、排除了哪些及原因、过了哪些校验（`data/qa.json`）。买卖类问题不回答，只给已披露的事实。
12. **核查记录**：每次构建校验了多少条引用、是否被拦下，记在 `data/audit.json`。
13. **预告偏差**：首次预告区间和定期报告实际数差多少、中间更正了几次。只陈列，不做判断。

## AI 的角色

| 环节 | 谁做 | 说明 |
|---|---|---|
| 抓取、分桶、权重、状态、时间、行情片段 | 规则 | `pipeline/fetch*.py`、`pipeline/build_events.py` |
| 判断是否同一事件、写合并理由 | 大模型 | 输出在 `pipeline/extracted/*.json` |
| 从公告和报道里抽说法、数字、类型、关系 | 大模型 | 同上，每条带原文引用 |
| 写分时点结论，区分事实、推断、不确定 | 大模型 | 同上，每句带证据编号 |
| 写预置问答和 trace | 大模型 | `pipeline/qa.json`，同样过校验 |
| 校验引用、数值、时序、来源级别、合规词 | 规则 | 不通过就不生成 `data/events.json` |
| 独立标注评测用的标准答案 | 另一个 Claude Opus 会话 | 不看抽取结果，先盲标，见 `eval/` |

为什么需要大模型：公告是长文本，更正公告要读懂"更正前、更正后、原因"；媒体标题里的问号、"或""有望"这类措辞决定它是事实还是推测；"审核未通过"和"交易终止"是两个不同状态。这些靠关键词规则做不准。为什么不全交给大模型：权重、状态和时间如果让模型自由发挥，结果不可复现，也没法审计。

**为什么不在网页上实时调大模型**：网页托管在 GitHub Pages，是纯静态站，没有地方安全存放模型密钥。所以大模型在本地离线跑，结果经校验后写进 `data/events.json`，网页只读这份文件。

## 评测

评测由另一个窗口独立做：标准答案不看抽取结果盲标，再和抽取结果对比，对不上的回原文裁决。标准答案是模型标的，不是人工标的，数值类可以靠原文复核，判断类的可靠性有限，详见 [eval/README.md](eval/README.md)。成绩、失败明细和陷阱用例的结果以 [eval/report.md](eval/report.md) 为准，这里不重复数字。

评测分两组看。测试集是抽取时没有参考过评测结果的 8 个事件，分数算独立测量；开发集是看过评测意见后改过的事件，分数只说明改对了没有。

评测查出并已改掉的问题：
- 第一版：国中事件漏了 8-20 的一次更正和两项指标，一处精度写错；19 个陷阱用例里管线只拦住 6 个。
- 第三轮：科达重组漏了 7-15 的发行价调整（10.80 元/股改为 10.50 元/股）和股东会决议；把媒体四舍五入的 74.75 亿元当成了一个版本；有三处冲突是误报（媒体说"否决"和公告说"未获通过"是一回事；公告前一晚上网造成的日期差不算冲突）。

据此给管线加了数值、时序、来源级别、新闻时间戳等检查。过程记在 [eval/adjudication.md](eval/adjudication.md) 和 [docs/AI使用与验证记录.md](docs/AI使用与验证记录.md)。

## 数据来源

| 数据 | 来源 | 用途 |
|---|---|---|
| 公告元数据和正文 | 巨潮资讯网（法定信息披露平台）公开接口 | 事实类证据、数字的各个版本 |
| 个股新闻、异动解读 | 扶摇金融数据 API（`/api/news/stock/timeline-list`、`/api/news/anomaly/analysis`） | 转述、观点、推测类证据，媒体发布时间 |
| 日 K 线 | 扶摇金融数据 API（`/api/a-share/prices/historical`，不复权） | 各次披露前后的价格和成交额 |

仓库里只放页面用到的部分：新闻只留标题、来源、时间、链接和一句引用；行情只留每次披露前后 3 个交易日。原始抓取结果不入库。iFinD MCP 没有接入。

## 怎么跑

网页不需要构建，直接看在线地址；本地看用任意静态服务器：

```bash
python3 -m http.server 8000
```

重新生成数据（需要 Python 3 和 `pdftotext`）：

```bash
python3 pipeline/fetch.py                      # 巨潮公告元数据
python3 pipeline/fetch_prices.py 600187.SH     # 扶摇日 K 线，需要密钥
python3 pipeline/fetch_news.py 600187.SH       # 扶摇新闻和异动解读，需要密钥
python3 pipeline/get_text.py <公告id>           # 取公告正文
python3 pipeline/build_events.py               # 组装并校验，生成 data/ 下的各个文件
python3 pipeline/build_events.py --dry <抽取文件>  # 只校验一份，不写文件
python3 pipeline/check_compliance.py           # 合规词检查
python3 pipeline/recheck.py                    # 重抓公告，比对正文指纹
python3 eval/score.py                          # 评测打分
```

环境变量（放在本地 `.env`，不入库）：

| 变量 | 用途 |
|---|---|
| `FUYAO_API_KEY` | 扶摇金融数据 API |

## 已知边界

- 事件是挑出来的样例，不是全市场自动发现。
- 抽取是大模型按 `pipeline/抽取说明.md` 离线做的，不是一条命令能重跑的程序；可复现的是校验、组装和评测。
- 披露时间：巨潮只给到"日"，公告实际是前一晚上网的；媒体时间精确到分钟。页面上两者都显示并注明精度。
- 更新时间：两个数据源都不提供"事后修改时间"。目前靠重抓比对正文指纹，2026-11-11 重抓 14 份公告，0 份有变化，所以更新时间都还是空的。
- 新闻证据用的是接口返回的标题和摘要，没有读全文。
- 行情只陈列事实，不做归因；"异动解读"的归因被标为推测。
- 已退市股票（如 605081）扶摇接口返回"代码不存在"，这类事件的行情栏会显示不可用。
- 传闻类证据目前没有真实样例。白鸽在线的澄清公告最接近，但只有公司的否认，没有抓到被否认说法的原始出处。
- 问答是预置的，不是实时生成；用户自己打字只能做版本查验和匹配预置问题。
- 港股事件没有行情和新闻数据。
